# RainyDays：以真实任务完成为目标的产品规划

## 定位与决策状态

用户已明确的方向：**供少量熟悉的同事或朋友使用的通用桌面助手，能够处理文件、研究资料、产出文档，并重复完成已验证的任务。**

用户已于 2026-09-28 授权按照本路线开始二次开发；实施进度见 [STATUS](STATUS.md)。首批工作修复资料截断与回答断流，结束以“100% Lux Desktop 对齐”为首版门槛的推进方式。旧总规范与 parity 文件保留为历史知识及安全约束参考，不能直接沿用其中所有功能和过程要求作为新版本的前置条件。涉及权限或执行保护的改变必须有明确的新契约和验证，不因目标调整自动失效。

判断依据见 [2026-09-28 评估](audits/baseline-2026-09-28.md)。核心策略是复用已有基础、减少同时推进的能力、交付完整的用户任务；不先重写运行时，不先把所有旧 WIP 卡补齐。

## 2026-09-29 进度校准

最新证据见 [二次重构进度审计](audits/baseline-2026-09-29.md)。R1 资料完整性与断流恢复、R2 文档输入到成果与继续修改均已通过确定性回归和真实 Electron 流程；新版对话与成果界面已完成。R3 只完成了快速产品测试与局部反馈缩短，重复治理和混合 WIP 仍未收敛。

R4 研究、R5 首次使用与默认能力收敛、R6 重复任务入口、R7 小范围内测尚未达到产品退出条件。Playbook、Routine、Browser、Media、Worker 和 Download 的代码或定向测试存在，不因此计为这些阶段完成。

当前执行顺序固定为：**R3 最小治理收敛 → R4 真实研究任务 → R5 首次使用和默认能力 → R6 单一重复任务入口 → R7 安装包与三人内测**。在 R7 前冻结 Media、远程 Worker、双浏览器后端和更多生态扩展。

## 第一版要交付的四类工作

| 工作 | 用户输入 | 合格的结果 | 首版范围 |
|---|---|---|---|
| 读资料并回答 | 选择文件/文件夹，提出问题 | 回答标明依据文件及位置，遗漏或解析失败可见，可继续追问 | 文本型 PDF、DOCX、XLSX、文本；图片采用经验证的视觉模型；扫描件明确提示能力限制 |
| 研究一个问题 | 问题与必要背景 | 搜索、阅读多个来源，区分事实与推断，输出可检查的来源和报告 | 一个经过验证的搜索渠道 + 网页提取；登录网页/复杂交互按后续实际需求加入 |
| 整理与产出文件 | 资料、输出目录与格式要求 | 可打开、可编辑的报告/表格；批量整理先展示变更，原文件可恢复 | 新建输出默认优先；Word 支持必要标题/列表/表格/引用，Excel 保证数据/表头/类型；复杂无损编辑后移 |
| 再做一次相同工作 | 保存成功任务的说明、输入规则与输出位置 | 手动重跑得到新结果，失败点明确，能调整后再跑 | 一种轻量任务模板，复用同一 Agent 运行链；验证通过后再加入本机定时触发 |

通用性来自可靠的文件、研究与受限代码执行能力；首版不需要向普通用户展示所有内部子系统。

## 用户应该怎样使用

1. 安装并配置模型，立即检测连接；选择本次工作的资料位置和输出位置。首次使用不要求理解 Persona、Oracle、Wire、Prism 或原生工具链。
2. 直接描述目标或添加文件。系统识别需要的能力；必要时用一句清楚的问题澄清成果要求。
3. 界面持续显示正在做什么、用到哪些资料、哪些输出已生成；普通新建输出沿用已批准的任务范围。
4. 覆盖、删除、越界访问、对外发送或扩大执行权限时，显示实际对象和影响，让用户作有意义的决定。
5. 结果集中为可打开的文件、来源和待处理事项；用户可以继续修改、取消或重跑。

默认界面聚焦对话、输入资料、结果文件。高级终端、后台子任务和调试信息可按需打开。设置只展示本版本真实生效的选项；旧配置兼容读取，避免删除用户数据。

## 能力与工程取舍

| 保留并优先改善 | 暂缓扩展 | 简化方向 |
|---|---|---|
| 会话、文件读取/编辑、搜索提取、文档输出、取消、恢复 | 远程 Worker/Relay、企业 MCP/Prism、全桌面自动化 | 一个可理解的任务运行链，默认只加载相关工具 |
| 凭据存储、Electron/IPC 保护、文件范围与数据备份 | 视频生成、HUD/Mascot、Anima、跨平台完整矩阵 | 高级功能不进入首版导航和首版门槛 |
| 必要时的现有隔离代码执行、进程树清理 | 自主多 Agent 编队、长期无人值守执行 | 先证明单任务结果质量，再增加并行或后台自主性 |
| 核心行为回归、真实安装包冒烟测试 | 每个普通功能的多角色证明链与完整真实性回执 | 一套通用测试目录与发布报告，避免逐卡复制 |
| 结果文件、来源记录和关键操作日志 | 企业级审计扩展和全 SQL instrumentation | 开发反馈与发布产物验证分离 |

浏览器 CDP 可在“必须处理互动网页”的已验证需求出现时启用一个后端；首版不同时养 CDP 与 Extension 两套完整能力。已有 Routine/Playbook/Worker/Media 的未提交代码先保护并标记状态，按需求逐项吸收，不以写了多少代码决定优先级。

## 必要的安全契约

- 每位用户拥有独立的本地数据与凭据；小范围分发不引入多人服务器或远程入口。
- 网页、附件、模型与工具输出均可能不可信；它们不能自行扩大任务权限。
- 用户选定资料范围和输出位置。宿主在每次操作时执行范围检查，模型不能绕过。
- 任务许可明确区分读取、新建、覆盖/删除、网络外发和进程执行；子任务与保存的重复流程只能继承已批准范围。取消或到期后许可失效；重启不默默恢复危险副作用。
- 允许用户在任务内批准范围内的新建输出，避免对同一意图逐文件询问。原文件覆盖/删除和敏感外发保留明确确认与可恢复路径。
- 保留凭据隔离、日志脱敏、IPC 鉴权、文件身份与越界保护、原子提交、备份迁移、取消与进程回收。
- 若启用代码执行，保留真实的系统隔离和受控网络/文件能力。隔离不可用时关闭该能力并解释原因，不能回退到未经限制的执行。
- 不把“全权限 Persona”或跳过授权当作体验优化。

这组契约应转换为一份小而固定的行为测试集。对新增安全复杂度，要求说明保护对象、可信攻击路径、为何现有控制不足、最小测试和维护责任；不因理论上可扩展就增加一套框架。

| R2 打通一个文档任务 | 最直接证明产品有用 | F5/F6 | R1 | 将 PDF/DOCX/XLSX 文件输入、模型理解、输出、预览、继续修改走通；任务范围内新建输出无需逐文件确认，权限回归保持有效 |

前两周重点是 R0–R3；同时只推进一个用户功能切片和必要的阻塞修复。R3 不能发展成新的全库测试框架重写。

**两周决策点：**至少两名目标用户在新机器/干净用户数据上，完成四类工作中的三个代表任务，结果可打开、有依据，并能继续修改。若仍主要受构建/授权/证明框架阻塞，冻结范围扩张，限时选择最小可复用运行部分；必要时比较将文件与桌面能力接到成熟 Agent 内核的成本。不要通过降低正确性或执行保护来通过这个检查点。

## 内测验收：测结果，不数工具

以下全部是**拟定门槛**，不是当前实测成绩。

- 固定 20 个脱敏任务，每类 5 个，每个至少跑 2 次，共 40 次。包含中文长文、表格、跨文件事实、网页失败和已有成果继续修改。输入与预期结果由人先定义。
- 总成功至少 34/40，每类至少 8/10。成功要求内容正确、结果可打开、关键依据可核对，过程中不需要修改源码或作者现场救场；普通澄清与必要审批不算失败。
- 对外发、越权写入、不可恢复覆盖、密钥泄露、重启重复副作用，专项验收发现一例即停止分发并修复；不能用总体成功率抵消。
- 三名首次使用者能够在说明指引下完成配置和首个任务；目标 10 分钟内完成，不要求安装 Node/MSVC。
- 记录首次反馈时间、总耗时、模型请求数、有效 usage、费用可用性、人工干预与审批次数；提供方不返回 usage 时明确标为未知，不伪造成本数字。
- 已批准范围内连续新建多个输出文件目标为一次范围确认；高风险动作的必要确认不计入减负指标。
- 安装包要跑干净启动、会话恢复、取消、文件生成、凭据保护和卸载数据策略；构建身份绑定在分发候选上完成。

真实模型评估应使用明确批准的测试配置和脱敏资料，不自动调用用户现有密钥。基础回归继续使用确定性测试以缩短反馈，二者不能互相替代。

## 开发与验证纪律

1. 每个改动先关联一个用户任务失败或已证明的维护障碍；没有对应收益的基础设施工作排后。
2. 快速检查做类型、lint、受影响行为回归。目标是多数日常反馈在约两分钟内，实际耗时需先测量。
3. 权限、凭据、路径和执行代码变化时，运行对应负向/恢复用例并独立审查；普通文案或功能调整不强制重走所有历史卡的完整角色链。
4. 新安装候选统一跑桌面、打包、恢复与完整性验证。数据迁移与取消等已有关键测试保留。
5. 治理清单或覆盖率红灯先区分“真实缺陷、来源身份变化、历史范围债务”。范围外问题独立记录，不悄悄吞掉，也不让一项功能无限追逐全库指标。
6. 覆盖率作为定位测试空白的信号，重点是高风险分支和真实失败用例；不要仅为了百分比增加镜像实现的测试。阈值改变如有必要应单独决策并说明行为保障，不在修功能时暗改。
7. 不先按文件大小拆 index/renderer/db；在已选任务中，提取能缩小调用 interface、集中行为和测试的 module。

## Later：用需求触发投入

| 工作 | 推迟原因 | 重新进入的条件 |
|---|---|---|
| MCP/企业连接 | 首版先证明本地任务价值 | 至少一个真实常用外部系统无法用现有能力满足，再做一个连接与明确授权 |
| 远程 Worker、Relay | 增加身份、网络和运维复杂度 | 用户确实需要跨设备执行，且本机版已稳定 |
| 双浏览器后端、全桌面自动化 | 维护面与风险较大 | 单后端/网页提取无法完成高频任务 |
| 多 Agent 自主协作 | 当前先解决资料与成果质量 | 任务评估证明单 Agent 的瓶颈是可并行工作，并且并行收益超过错误与费用 |
| 无人值守调度 | 放大重复副作用和权限问题 | 手动重跑可靠，持久去重与权限范围已经验证 |
| 图像/视频/HUD/Anima | 不属于首版四类工作的必要条件 | 内测用户持续提出、能够解释实际价值 |
| 跨平台、公开分发、自动更新 | 会扩大测试与供应链责任 | Windows 小范围内测通过，明确维护人、签名/更新渠道和支持能力 |
| 深度企业审计/完整真实性证明 | 当前用户范围不足以支持成本 | 明确客户要求或新的可信威胁，而非为对齐而实现 |

## 本路线建议停止的目标

- 将 Lux 的所有工具名称、内部行为、生态和界面逐一复刻作为产品成功定义。
- 将每张普通卡的角色切换记录或源码哈希全绿当作真实任务成功的替代。
- 为未出现的用户需求继续增加默认工具与设置。
- 用放宽全局权限、禁用隔离或静默截断内容换取表面可用。
- 在没有真实任务数据前承诺完整完成率或确定发布日。

优先恢复的能力是：用户给出资料与目标后，RainyDays 能读到足够的信息、在明确范围内连续完成工作，并交付可检查、可继续使用的结果。
