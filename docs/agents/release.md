# 同事版发布、升级与维护

本文件是D13–D18与A13共用的执行清单，**不是已经存在合格安装包的声明**。D18是基础工作流出口，完整通用版必须通过[通用验收](general-agent-acceptance.md)。发布状态见STATUS。

## 候选包

沿用现有 Electron/NSIS 和 package.json 的构建路径。先确认依赖锁、原生 SQLite/解析 worker/隔离宿主能进入包，再测试已安装入口。固定应用 ID 与用户数据位置，避免改名导致“数据丢失”。

开发机装有 Node、构建工具，不能证明同事机器可用。至少在两套干净 Windows 标准用户环境完成：
1. 安装、启动、退出、第二次启动；中文/空格用户名和安装目录。
2. 无 Node/npm/MSVC 的环境下完成模型配置、读文件、生成与打开成果。
3. 无部门盘、缺工作目录、只读输出目录、模型无额度时仍有可操作界面。
4. 取消任务与退出回收后台；只关闭窗口与真正退出的区别准确。
5. 旧数据副本迁移，原会话/附件/成果可读；升级中断和恢复，不复制旧任务许可。
6. 卸载时明确是否保留用户数据，重装不会无提示覆盖或删除。

已有 packaged 测试覆盖的行为直接复用。若旧 runner 被范围外清单阻断，保留失败证据并用同一个候选运行相关既有测试，修最小连接问题；不能把跳过整个发布层叫通过。

## 发布资料

完整候选另外验证：Windows观察/输入helper随包运行、真实图像传递、受支持浏览器连接、MCP本地进程与远端登录、CLI项目依赖提示、技能/子任务。普通用户路径无Node/npm/MSVC也能完成文件/文档/原生桌面任务；代码项目所需工具与第三方MCP服务器运行时单独声明，不能暗示安装包包含所有依赖。

至少一套开发依赖齐备环境完成代码→测试→浏览器检查；两套干净环境验证helper、协议与退出清理。只回收应用拥有的资源，不关闭用户原有应用或浏览器。具体版本、DPI、多显示器与服务器测试矩阵写入同一发布记录。

一个候选仅需一份发布记录：版本/commit/包摘要、支持系统和模型、验收结果、已知限制、安装/升级/恢复步骤、反馈入口。包摘要只用于确认拿到同一文件，不扩展成每票证明链。

代码签名状态必须真实说明；内部试用若未签名，记录 Windows 提示与人工核验方式并让试用者知晓，不教同事关闭安全软件。稳定交付采用什么签名/分发渠道由 D13 实际环境和组织要求决定；没有证书时明确约束，不暗示已签名。

分发前检查依赖许可证和打包内容，不夹带用户 config/vault、旧数据库、私有素材或 Lux bundle。复用构建已有排除规则和检查，不另造供应链平台。

## 升级和回退

- 升级前先通过现有备份链获得一致快照，确认可读；数据库与关联附件/配置范围要清楚。
- 迁移不可自动回退为旧 schema 时，旧版本读取必须拒绝并给出恢复流程。回退前保存新版本新产生的数据；不能直接复制旧库覆盖。
- 成果通常在用户选择的输出目录，升级/卸载不得当缓存删除。用户选择清空数据时准确列出会删除什么。
- 可用的恢复入口和文案必须在 UI/指南中落地，不能只交付开发脚本作为普通同事恢复方式。
- 只在用户明确选择后恢复；中断任务显示待处理，不自动重放写入。

## 发布 gate

基础Beta/稳定里程碑沿用D15/D16/D17/D18条件。完整通用Beta须达到100次目标85分、每组8/10并有全能力安装证据；稳定通用版须A13全部条件、100次目标95分且每组9/10，以及覆盖新增能力的同事试用。均无未解决P0/P1。PR合并、构建成功或旧报告通过不单独构成发布。

研究或模型费用无授权时暂停真实调用；试用用户/机器不足时保持候选，继续能独立完成的文档或缺陷修复。不得将“作者自己运行三次”写成三人试用。

## 发布后维护

指定一名维护者和一个真实反馈渠道；未指定时 D18 不通过。反馈默认为版本、错误编号与用户描述，诊断包由用户预览后主动提供，不自动收集文档。

P0 立即暂停分发并通知受影响使用者处理；P1 优先修复并提供可复现绕行方式；P2 每周集中排序。通知与外部发送由发布者明确授权执行，Codex 不擅自给同事发消息。

每周一次核对模型可用性、主要失败类别和支持负担；提供方变化时只重测受影响兼容行为。用户升级到已验证版本前保留可恢复数据。每月根据实际使用决定一项扩展，不以“Lux 有这个功能”作为投入理由。
