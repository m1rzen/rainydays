# GLM 审查交接规范

文档与交接写法如有冲突，以[执行流程的文档规则](workflow.md#文档各自负责什么)为准。

适用于每次 GLM 开发、修复、返工结束后提交给 Codex 的审查。执行要求见 [GLM 任务执行规范](glm-execution.md)；任务排期只由 [plan.md](../work/general-agent/plan.md)维护。

生效：2026-11-17。

## 交接方式

每轮生成一份内部 Markdown：`docs/work/<当前effort>/handoffs/YYYY-MM-DD-<ticket>-<topic>-rN.md`。普通多切片同轮可以合并一份，用表逐项对应；返工递增 rN，链接上一轮，保留原失败记录。不要用交接文档替代原票据、审查记录或总路线。

说明与源码一起交付，最终回复给出交接绝对路径、起点/审查终点和“待独立审查”或“未达提审条件”。文档中的仓库内链接保持相对路径，原始日志给审查机可读取的绝对路径；跨机器提供脱敏证据副本或可重建的合成复现，真实凭据由审查者本机读取，不写入说明。

**必填内容：范围、最终版本、逐项验收、测试原始结果、正常入口证据、未完成项、重跑方法、状态与审查请求。** 无关分支可写“不适用＋原因”，必需证据缺失写“未执行＋原因＋下一步”；模板占位符必须替换。

## 版本和证据要求

- 起点 SHA 和审查终点 SHA 都写完整 40 位，并说明哪些提交/路径不属于本轮。产品受测版本与最终受审版本可以因文档提交不同，必须明确记录源码/测试差异。
- 优先提交产品代码与测试，再验证该版本；后续只补交接文档时在最终回复注明文档提交 SHA。提交前验证的，提供 HEAD、受测差异文件及补丁 SHA-256；提交后确认产品源码/测试字节相同。避免为写入交接文档自己的 SHA 反复提交。
- 最终受审产品源码、测试或相关依赖与受测内容不一致时，先补受影响验证，再生成新交接。仅文档改动做对应文档检查，不机械重跑产品全套。
- 截图、日志、录屏注明所属验收项和版本。截图必须能看到被验证状态；UI DOM 检查、截图、真实点击路径分别标明，不能互相冒充。
- 每个完成声明都链接证据。日志不可读、命令不能重跑或证据版本不明时，该项写“证据不足”；统计只使用本轮实际结果，首次失败、修复复试及历史成绩分列。
- 原始敏感诊断按仓库规则留本地；交接里说明清理/恢复方式，保留审查需要的脱敏事实。审查前保持证据可取得，不删失败日志。
- 返工完整列出原审查全部问题 ID，分别注明本轮处理、未处理或已有独立关闭证据；“已修待复审”由 GLM 提交，“已确认修复”只引用独立复审记录。

## Codex 接收与复审规则

1. 先核对实际仓库、固定范围与 TESTED/REVIEW_HEAD，检查本轮改动和其他 WIP 的边界。材料缺失时记录“证据不足”，继续能独立完成的源码与行为核对；不把缺字段直接等同于代码必然错误。
2. 顺序独立核对工程正确性和规格符合度。优先真实用户链路、原缺陷和未确认假设；测试为绿是输入证据，不自动构成审查通过。
3. 在原 effort 的 reviews 下保存结论：问题 ID、严重度、代码位置、预期/实际、重现命令、影响、修正建议及验收条件；引用交接，不覆盖 GLM 原始执行结果。
4. 范围内缺陷用 changes-requested 并返回原票 in-progress；后续无关项回原有路线入口。没有阻塞发现且必需证据齐备才进入 reviewed；verified 继续按票据全部验收判断。
5. 新轮返工逐项标记“已确认修复/仍可复现/证据不足/未处理”，关闭动作引用新证据与版本；未复核问题保持原状态。审查后源码改变，结论只覆盖已审版本，新增变化提供增量复审。

## 发给 GLM 的任务开场指令

> 先读 AGENTS.md、docs/STATUS.md、docs/agents/glm-execution.md 和 docs/agents/glm-review-handoff.md，再按当前 plan 与票据执行本轮任务。开工先固定基线与逐项验收，涉及返工逐条读取原审查问题；完成正常用户链路及对应验证。每轮结束提交一份填写完整的审查交接说明，附固定审查版本和可重跑证据，交由 Codex 独立复核；未满足项保持实际状态。沿用已批准范围自主推进。

## 发给 Codex 的审查指令

> 请按 docs/agents/glm-review-handoff.md 审查这份交接：<交接文件绝对路径>。先核对固定版本与证据，再分别检查工程正确性、规格符合度和原问题是否修复，必要时从正常入口独立重现；将结论落入原 effort 的 reviews 并同步原票状态。本轮只做审查，产品修复另按用户任务范围执行。
