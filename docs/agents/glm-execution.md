# GLM 任务执行规范

文档与交接写法如有冲突，以[执行流程的文档规则](workflow.md#文档各自负责什么)为准。

生效：2026-11-17。适用于 GLM 在 RainyDays 中的开发、缺陷修复和审查返工。按用户要求，基于 [2026-11-16 独立审查](../work/general-agent/reviews/2026-11-16-glm-improvements-code-review.md)制定；它补充 [workflow](workflow.md)，排期仍只由 [plan.md](../work/general-agent/plan.md)维护。

**交付单位是经过正常入口验证的用户行为。代码、文件、工具回执和新增测试分别只是证据的一部分。每轮结束按[审查交接规范](glm-review-handoff.md)交付固定版本，由 Codex 或用户指定的独立审查者复核。**

## 1. 开工：固定范围与基线

1. 读取 `AGENTS.md`、`docs/STATUS.md`、总路线、当前票据及其最新审查；仅补读受影响链路的架构和契约。承接返工时逐项读取问题的重现条件，而不是只看标题。
2. 记录仓库绝对路径、分支、完整起点 SHA、已有工作树修改及所有者。原有未跟踪文件、用户数据和凭据保持原样；精确暂存本轮文件，本地提交且不自动推送。
3. 在原票据写一张开工表，每项验收先定义可观察结果与验证入口；注明本轮包含哪些问题、哪些明确留在后续票据。一个切片完成一条用户路径及必要依赖修复，不把其他路线任务并入“顺手修复”。
4. 运行受影响的既有检查，保存首次结果。复用相同源码、环境且可核对的近期基线时，写出来源。遇到失败先保存事实，再用最小对照辨认原因。

验收沿用已批准要求。看到失败后，不得通过缩小统计分母、改写正确结果或把范围内问题移出本轮来宣称完成；范围确有修订时保留原要求、变更理由及用户的明确决定。

开工表格式：

| 验收项/问题 ID | 用户可观察的预期 | 正常入口与最终观察点 | 失败/边界场景 | 计划证据 |
|---|---|---|---|---|
| AC-01 / Rxx | 明确输出、状态或行为 | 如普通会话→工具→持久化→会话 API→界面 | 如相对路径、前置失败后重试 | 测试入口、日志或人工步骤 |

**进入实施的条件：每个本轮验收项都有预期、入口、最终观察点；基线和他人修改有记录。** 已批准范围内的常规实现自行推进，具体授权沿用会话记录；新增外部操作、模型调用和用户数据操作遵循仓库既有规则。

## 2. 实施：先理解契约，再修改完整链路

- 从用户入口沿调用链读到结果消费方，核对参数解析、权限/路径网关、真实返回结构、消息持久化、恢复、通知和界面。只改变相关节点；新增字段必须核对其消费方。
- 阅读所用内部 API 的实际实现。测试替身使用相同的限制、错误和返回结构；路径网关、持久化、流终态及技能发现的关键验收至少一次经过真实本地实现。`maxBytes` 等参数的语义以实现和契约为准。
- 已知功能缺陷先取得能失败的行为复现，确认失败原因是目标缺陷，再修到通过。保留有意义的回归入口；可用同一公共链路覆盖相关问题，无需为每个实现分支另造测试。
- 提示词、注释和文件正文可以辅助能力，运行行为由正常入口的实际结果证明。需要宿主状态或持久化的要求在相应运行链实现。
- 既有测试失败时，区分产品错误、替身假设过窄及历史失败。测试确需适配新消息顺序时，说明原假设和新语义，保留原用户行为断言；不得用删用例、跳过、放宽结果或改清单掩盖行为回归。
- 复用现有 Agent、路径网关、技能与票据机制。把新发现的无关问题记入原有后续入口；不另建执行平台、状态体系或第二条排期。

**实现就绪的条件：用户入口可达、结果消费者已接通，已知缺陷的正确行为断言变绿；只有局部文件或单元测试通过时继续实施。**

## 3. 验证：按变更选择必须走通的路径

代码变更执行 workflow 规定的当前产品检查，并按下表补受影响链路。命令从当前 `package.json` 和测试文件取得；基于 dist 的 HTTP/Electron 检查先构建当前源码。纯文档、低风险文字/样式修改只做相应链接、一致性或视觉检查，不增加无关测试。

下表是条件性验收要求，不是另一条任务队列。R 编号指本次审查的对应问题。

| 触发的改动 | 最低行为证据 |
|---|---|
| 收敛、循环或停止规则（R01） | 实际生成/修改文件的连续命令能完成交付；无进展检查有界停止；失败调用不冒充进展；普通任务路径仍工作。观察实际产物与最终回答，不能只数工具名 |
| 成果路径或登记（R02） | 绝对/相对路径、中文/空格路径经真实授权网关解析；工具回执、持久化消息、会话 API 和列表指向同一文件；重载后仍可找到正确版本 |
| 截断、失败、取消或终态（R03） | 正常完成与未完成分别贯通 Agent、HTTP 事件、持久记录、通知和界面；残缺工具参数执行次数为零，已完成写入保留；等待续接不能报 completed |
| 声称章节/任务可重启恢复 | 在隔离数据中真正终止并重新启动进程；保存并核对输入版本、环境、完成章节、产物版本和下一步；变更输入后的过期检查点可识别；取消后恢复不重复章节或最终发布。同一 Agent 输入“继续”只证明同进程续接 |
| 技能、模板或人格（R04） | 用实际采用的加载路径证明内容可达：包式技能走目录→skill_open→模型请求；旧平铺技能走人格绑定→实际提示。仅放置文件或读取其正文不算接入；声称支持开关时验证启停效果 |
| 幂等、重试或消息去重（R05） | 前置失败后合法重试成功；并发/已受理请求按契约去重；网络重放与 UI 逻辑键关联；两次合法相同文本保留。原案调查关联客户端事件、请求、run 与持久消息；内存去重范围和重启边界明确 |
| 回执与第三方结果（R06） | 可信工具名称、匹配调用 ID、成功状态及必要字段均校验；未知工具、失败/截断结果和伪造路径不能登记为已验证成果 |
| 大文件、格式或摘要（R07） | 真实网关验证声明支持的大小边界及超限行为；读取范围和拒绝阈值分别实测；实际内容与格式一致性有依据，头部摘要与全文件版本摘要区分 |
| 图像缓存或清理（R08） | PNG/JPEG 混合、重复版本、超过容量后的索引与磁盘一致；有界缓存确实删除被淘汰文件，停止/失败不遗留任务拥有的临时资源 |
| 新成果格式、类别或 UI（R09） | 从正常会话/API 数据到真实 Electron 显示格式、角色及操作；覆盖 source/intermediate/deliverable。直接注入渲染数据可定位 UI 问题，但不能替代登记至 UI 的完整验收 |
| 文稿模板或语义质量 | 固定原材料、上下文和预期；独立标注六类事实风险，分开记录事实、表达和版式结果；真实模型表现单列。样本字段检查只证明夹具结构，篇幅按本次用户要求处理 |

执行记录规则：

1. 记录以实际工具输出和观察为准，预期与实际分列；没有执行就写“未执行”，不得推算成功数、补写不存在的日志或把计划操作说成已完成。每条必需命令记录时间、cwd、运行环境、完整命令、退出码、通过/失败/跳过/取消数和日志路径。串联脚本中断后，后续阶段写“未执行”；需要其结论时单独运行并记录。
2. 首次失败与修复后复试分列。声称历史问题时，提供同环境、明确旧版本的对照；只替换一个模块的对照就明确写“模块对照”。缺少对照时标“原因未确认”。
3. 模拟模型、真实本地工具/HTTP、真实浏览器/Electron、真实模型、当前安装包分别说明。每种证据只支持其实际范围；未执行的质量或安装验收保持未验收。
4. 保存可供审查者独立运行的回归测试、合成材料生成方法和命令。正常回归进入已有测试目录；临时探针可留本地，但决定性结论须有可移交的脱敏步骤或合成复现。原始诊断、用户数据和凭据不进 Git。
5. 同一失败两次没有新证据，改做能区分原因的最小实验；达到明确通过条件后结束复核。有代码、测试或依赖变化时重跑受影响检查，不能复用变更前的绿色结果。

**自测通过的条件：所有本轮必需行为有对应证据；本轮引入的回归和范围内缺陷清零；未执行、失败及确认的历史问题如实分列。历史失败只有在基线已证明、与本轮无关且不阻塞本轮用户路径时才能作为明确继承缺口。**

## 4. 自查：分别检查工程正确性与规格符合度

先按工程正确性查调用者/消费者、状态、错误、持久化及资源清理，再按开工表逐项核对用户结果和规格；两份结论分开写在交接表。核对至少包括：

- 结果从正常入口到达用户，工具成功与用户可见状态一致。
- 默认、失败、取消、重试和本轮承诺的恢复行为都有实际观察。
- 检查使用最终产品源码和测试版本；测试之后的行为变化有新的结果。
- 完成声明的范围与证据相等。“构建通过”“新增测试通过”“已有真实模型成绩”均不自动扩展成本轮产品已验收。

自查发现缺陷继续修复；超出本轮授权或依赖外部事实时保留未完成，并给出下一步与归属。自查是提审准备，独立审查结论由审查者填写。

## 5. 状态与完成用语

继续使用原有票据状态，不新增状态枚举；“待独立审查”只作为交接结论。**表中状态评价整张票据；单个切片的自测通过只记入该切片，整票尚有未实现工程或范围内缺陷时保持 in-progress。**

| 状态/表述 | 使用条件 |
|---|---|
| `in-progress` | 正在实施、自测有本轮问题、必需工程证据不足，或独立审查要求返工 |
| `blocked` | 存在明确外部阻塞，写明已完成范围、阻塞事实和解除条件；其他可独立工作可继续 |
| `implemented`；“工程自测通过，待独立审查” | 该票全部工程范围与必需工程检查完成，无未解决的范围内缺陷；产品质量、安装等尚未覆盖的条件明确保留 |
| `reviewed` | Codex 或用户指定的独立审查者核对固定版本后通过。GLM 自查不将自己的票据推进到此状态 |
| `verified`；“验收通过” | 在 reviewed 基础上满足该票当前全部验收，由独立审查/验证记录或用户明确确认支撑 |
| “里程碑/全部完成” | 该范围全部验收项已验证，阻塞缺陷关闭，剩余项不属于所声称范围；不能用若干切片 implemented 代替 |

已有历史验证保留版本与范围；新增实现改变了受影响行为时重新取得证据。GLM 可以提交可审查的未完成切片，但应写“未达提审条件”及实际票据状态，不能以提交本身推进完成状态。

## 6. 提交、交接与返工

1. 按[交接规范](glm-review-handoff.md)填写一份交接说明，链接原票据和本轮证据。复用票据/STATUS 的事实，其他入口只给摘要与链接，避免复制多套完成清单。
2. 核对 diff、精确暂存、本地提交；固定产品受测版本和交接审查终点。用户 WIP 可存在，但须与受审差异区分。记录源码/测试在验证后是否变化。
3. 票据和 STATUS 同步实际状态，依赖或执行顺序确需变化时才更新 plan。交接路径与审查范围随最终回复交付给用户，由用户转交审查；不自动向其他会话或服务发送消息。
4. 审查出现范围内 P1/P2 后，原票返回 in-progress。按问题 ID 写根因、修复位置、失败前证据、修复后证据及受影响回归；原始失败记录保留。GLM 标“已修，待复审”，由审查者关闭。
5. 复审交接同时提供原始范围和本轮增量范围，完整对账原审查问题 ID；本轮未处理的逐项保留。自查认为发现不成立时，提供可重复反证并交审查者裁定。等待审查期间可以按原路线推进无依赖的已批准工作；待审版本后续变化另交增量，不能沿用旧证据。

**每轮结束的条件：版本固定、证据可取得、交接字段完整、状态与剩余问题一致。**
