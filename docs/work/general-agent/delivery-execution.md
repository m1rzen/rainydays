# RainyDays 完整版交付执行规范书

2026-11-18，供实施开发者、独立复核者、发布维护者及参与试用的同事使用。本文把批准路线转换为操作步骤和验收证据。每次开工从[总路线 §6](plan.md)选择当前票据，整票状态回写原票；基础和最终分数分别按[基础验收](../../agents/acceptance.md)与[通用验收](../../agents/general-agent-acceptance.md)裁定。现状和本轮复现实验见[交付复核](reviews/2026-11-18-delivery-readiness.md)。

## 一、首次接手与候选冻结

1. 实施者读取 STATUS、当前票、最新失败记录；运行 `git rev-parse HEAD`、`git status --short`，记录本轮起点、既有 WIP 归属，以及需要从普通用户入口看到的结果。按票据区分同事模式与显式开发模式。
2. 发布维护者在独立工作目录固定产品和测试提交，保留原工作目录。使用锁文件的依赖和 manifest 指定的模型资源；执行 `npm run models:check`。记录 Node/npm、Windows、模型别名、解码/思考设置、构建 ID、源码摘要。以 11 月 18 日的五个桌面 WIP 输入为首个核对项。需要它们的行为经归属和验证后再纳入；临时测试文件不得默默改变候选身份。
3. M3 可先冻结源码/构建，由 D13 同步准备相同源码的包。各自记录运行入口，得到安装器后补包 SHA-256、签名实际状态与安装环境。源码回归与安装验证各自计分。正式 A13 开跑前必须绑定冻结安装候选。
4. 实施者把每个场景的输入文件及摘要、提示词、预期结果、允许交互、评分人、超时和费用上限写入当前评测记录。真实调用核对**模型配置、次数、费用、允许材料**四项授权；已有授权按原范围沿用。资料缺许可时准备脱敏夹具，缺预算时继续工程回归、包内清单和评分表准备。
5. 先重现[中文格式缺陷](reviews/2026-11-18-delivery-readiness.md)，在 A13 成果登记切片修复并独立复核；将样本收入 M3-04。可以同步准备全部场景。若已开跑后改变受测代码或输入，保留原窗结果，新版本的复试单列，再冻结正式计分窗口。

## 二、M3 质量窗口操作卡

评测者按下表从**普通会话**运行八个场景，每场景三次。固定场景号、轮次和执行模式。故障注入用于判断工程行为，真实模型用于判断内容和选择；同一场景同时需要两类证据时分别记录。一次运行包含的人工核验和接手写在同一行。

| ID | 准备与执行 | 评分者实际检查 |
|---|---|---|
| 01 简单文件 | 提供短材料和明确用途，要求生成并登记一份初稿；从成果区打开，再重启找回 | 首次可用稿耗时、关键字段、文件存在、角色与会话一致，篇幅符合本次要求 |
| 02 多材料文稿 | 固定经许可的原料、提示和事实对照表；从普通会话调用纪要技能，交付 Word。给独立评分者原料和匿名成品 | 六类事实分别追溯原句，包括金额上下限、统计主体、包含关系、风险维度、意向程度、无依据执法结论。按现有夹具事实 50%、语言 30%、版式 20% 分项记分；评分尺度、必对事实与通过线在运行前冻结，关键数字/主体错误单列。另记录目标软件能否打开、编辑与另存 |
| 03 小字与页图 | 准备 PNG、JPEG、带页码/版本的预渲染页面和已知问题；让模型指出位置、修改后重读 | 宿主确实附了像素，观察能对应页码、文件摘要和修改版；评分者对照具体错行、小字或裁切。无真实自动渲染能力时只声明预渲染覆盖 |
| 04 成果归属 | 提供输入 PDF，让脚本生成中间文件和中文 Markdown，并保存一份下载成果。覆盖中文/相对路径、跨 4096 字节字符边界、较大文件 | 回执、消息重载、成果区的路径、角色、格式一致；独立读文件比对全量 SHA-256；打开交付件，原材料可区分。异常或取消时核对是否曾错误发布成功 |
| 05 长文续接 | 从已有写入边界截断，保留一组不完整的工具参数；重启再“继续”，另测输入已改变 | 终态为 incomplete，残缺参数零执行；未变版本只补缺章，已变版本停止盲续。逐章核对有无遗漏/重复，再由评分者核对事实。记录首件产物前中断的实际提示 |
| 06 取消、突然退出 | 使用可确认写入边界的长任务。分别在写成后取消、进程退出、再次打开并确认恢复 | 已写文件可读、可核对；取消反馈与进程清理计时；无新增写入，结果和待办可区分，版本不同须交用户决定 |
| 07 受理和重试 | 从发送入口覆盖前置失败后重试、在途重复、完成后同键重放、合法同文新请求 | 数用户消息及 run，记录逻辑请求 ID、进程、时间窗；同进程窗口内同一受理请求仅一次；合法新请求独立。区分请求重放与已提交工具写入的恢复 |
| 08 编码组合交付 | 在带未提交改动的小型 JS/Python 项目中给出可重现错误，经默认助手修改、运行测试、解释差异并登记成果 | 用户原改动保留、退出码真实、生成命令未被误停；重读交付件。模型未能修正、环境缺依赖、运行被取消分别记结果 |

评分者在首轮和修复复试均保留输入版本、耗时、错误与介入。模型等待、工具执行、端到端和人工时间分列；并发时间不能直接相加。原始任务一次约 58 分钟只作参照，不设事后速度门槛。M3 退出沿用总路线要求，完成 24 次同候选记录、范围内 P1/P2 清零、成果可打开并正确归属、状态恢复可靠且事实达到冻结标准。若还有失败，按原因派回原票；Beta/稳定分数留给各自正式窗口。

## 五、D15–D18 与 A13 的发布判定

| 决策 | 进入和通过要求 | 谁核对 |
|---|---|---|
| 基础候选 D15–D18 | D15 所列依赖完成后，以 F/R/O/T 各五题、每题两个独立会话取 40 次。基础 Beta ≥34/40、各组 ≥8/10，稳定 ≥38/40、各组 ≥9/10，完成基础试用、问题修复、指南和维护交接 | 评测者冻结预期，独立复核者看原件与失败记录，维护者签收交接 |
| 通用 Beta | F/R/O/T/C/L/M/B/W/S 十组，每组五题，各运行两次。当前安装包所有必需类别可用，≥85/100 且各组 ≥8/10，未结 P0/P1 为零 | 发布维护者按包摘要、支持矩阵、总分及分组分数做决定 |
| 稳定通用版 A13 | 同一冻结候选 ≥95/100，各组 ≥9/10，未结 P0/P1 为零；D18 与 A13 各能力依赖闭合；两套干净环境、恢复、S04/S05、试用、指南、维护人及真实渠道全部取证 | 独立复核者核分，发布维护者交付已验证的同一包 |

**计分。** 首次运行的 blocked、超时、提供方或额度失败都留在分母，修复复试保留关联但单列。基础默认 5 分钟、新增类别默认 10 分钟，GUI 至多 50 动作、编码至多 3 次自动修正；例外及费用须事前冻结。相同候选、输入、预算、评分和实际运行均匹配时，基础 40 次可计入 100 次。M3 的 24 次单独报告。按基础验收另记十次冷启动（目标每次 ≤10 秒）、发送与取消本地反馈 ≤1 秒、进程清理目标 ≤5 秒、20 轮取回、两小时混合运行及十次重启。

**试用排法。** A13 至少三位目标同事，五个工作日、每人至少八项、总计至少 30 项，≥90% 无作者救场；至少一人实际使用代码/CLI。C/L/M/B/W 各至少三项，基础四类各至少两项；每项仅计一个主要类别。若希望一次窗口同时满足 D16，须同时满足 D16 三位非开发同事、各基础类至少五项和十分钟完成配置及首任务等条件。按唯一主类计算，四个基础类共至少 20 项，五个新增类共至少 15 项，**合并窗口至少要安排 35 项**。可让实际使用 CLI 的非开发同事参加，或增加适当参与者；达不到共同覆盖时分别记录两轮，不能把任一规则降到 30 项。合并安排属节省重复工作的选择。

**排期与资源。** 当前可并行安排 M3 的材料、独立评分和 D13 清单处置。M3 冻结后按八场景公布三次结果；D13 首个同版本安装器出来后安排两机验证。提前落实可用模型与预算、外部 MCP 账号、真人接管、双屏及目标 Office 环境、三位同事和一名维护者。维护者在 M3 结束、首个可安装候选、通用 Beta 三处分别重估剩余工程日、外部等待和五个工作日试用。原计划的 58–96 工作日是从早期起点做的估算。目前两项关键数据是 D13 剩余真实差异和 M3 实际失败分布，缺少这两项时不承诺稳定版日期。

## 六、开发、审查和交接

每个切片用原票记录下列三行，再实施最小改动。GLM 依[执行规范](../../agents/glm-execution.md)与[交接模板](../../agents/glm-review-handoff.md)提交，独立复核者沿正常入口复跑。无需逐票重复请示已经批准的路线。

| 时点 | 必填内容 | 产出位置 |
|---|---|---|
| 开工 | 起点 SHA、用户动作、预期可观察结果、相邻调用者/消费者、现有失败、依赖和试验授权 | 原票执行记录；测试夹具只含脱敏输入 |
| 完成一条路径 | 普通入口 → 执行 → 状态/成果持久化 → 界面打开或失败恢复；按实际风险覆盖取消、重试、版本冲突和重启，各写期望与实际。提交自己的变更后核对受测与审查版本 | 工程用例及忽略目录原始日志；原票逐项列命令、退出码、通过/失败/跳过、构建与证据链接 |
| 移交 | 工程结论与规格符合度分别写，列未测项、阻塞条件、可并行工作、回退与接手人。每个缺陷写用户影响、复现、预期／实际、原票、修复版本与复试 | GLM 自测整票满足工程范围最多标 implemented；独立审查后按证据推进 reviewed/verified。STATUS 指向最新事实，只有总路线维护执行顺序 |

单次运行最少记录「场景/轮次、候选/模型/环境、输入与预期版本、首反馈/首稿/完成时间、调用次数/usage/费用或未知、成果及来源、人工澄清/审批/纠错/救场、pass/fail/blocked、缺陷与复试 ID」。原始日志保留本机，提交脱敏摘要。每周看失败最集中的用户结果及解决它所需的最小改动。首次可直接派发的工作为 **M3-04 中文格式回归及八场景冻结材料**，同时由发布维护者处理 **D13 当前清单首个拒绝点**；两项均已有可复跑的起点。
